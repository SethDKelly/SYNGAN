## Core separation

007-G preserves this authority chain:

```text
semantic Strategy / method / activity commitment
        ↓
implementation binding selection
        ↓
exact dependency + executable closure resolution
        ↓
identity / integrity / trust / compatibility
        ↓
current authorization + network/egress qualification
        ↓
runtime-role distribution closure
        ↓
immutable Attempt invocation
        +
current scoped capabilities / secret access
        ↓
physical runtime realization
        ↓
non-final physical/method result
        ↓
owner semantic validation
```

No installed package, plugin class, model object, entry point, worker image, runtime job, authorization grant or secret becomes semantic authority merely by existing.

## Semantic versus executable binding

Synthesis Strategy remains reusable synthesis-behavior authority.

Implementation binding remains revisioned integration state describing which exact executable realization can satisfy which semantic Strategy/method contract and under what conditions.

The design keeps separate:

```text
Strategy semantic revision
implementation-binding revision
implementation component/package build
SPI/runtime-contract version
Learned-State representation/codec version
platform/runtime version
```

A binding may narrow Strategy capability but cannot silently broaden it.

Evaluation-method executable binding remains architectural and does not create an Evaluation Method concept.

## Attempt realization and compatible retry

Every material Attempt freezes one exact executable/dependency closure in an immutable invocation context.

Runtime cannot hot-swap a missing dependency, model, tokenizer, service, binding or codec inside that Attempt.

A later Attempt may use another compatible binding only when the unchanged semantic activity did not commit an exact implementation and the new realization preserves its semantics/network/dependency contract. The later Attempt receives a new exact invocation/history record.

If the actor committed the exact implementation for compliance/reproducibility or changing implementation alters semantic meaning, another binding cannot be substituted without a new semantic commitment.

## Composite implementation closure

One Strategy binding may resolve multiple material components such as tabular code, source-derived text code, native libraries, codecs and immutable model/state artifacts.

One Strategy does not imply one package or one model.

The exact Attempt needs a bounded closure identity/representation strong enough for its historical and reproducibility claims, while the concrete closure schema/digest technology remains deferred.

## Dependency boundary

007-G distinguishes:

```text
dependency requirement
resolved concrete dependency
identity match
integrity/authenticity
trust/approval
runtime compatibility
semantic/activity compatibility
current authorization
network/egress compatibility
```

A mutable package name, registry tag, path, URL, cache alias or model alias does not substitute for exact historical identity unless its provider contract genuinely provides immutable identity semantics.

## Acquisition boundary

Provisioning/acquisition may occur explicitly before material execution when the selected profile allows it.

Acquisition success does not itself establish trust, compatibility or permission.

During an Attempt, a missing dependency may not trigger hidden package installation, public model-hub access, artifact download, remote-service fallback, telemetry activation or dependency replacement.

## Trust / supply-chain boundary

Installed/discovered does not mean trusted.

Where policy requires it, executable/artifact eligibility may depend on exact identity, integrity/authenticity, approval or other supply-chain evidence.

Third-party extension metadata discovery remains distinct from importing/executing provider code. Unsafe code-executing state deserialization is likewise a trust/security boundary rather than ordinary decoding merely because the codec is technically available.

No signing/SBOM/scanner/attestation product is selected.

## Network / egress boundary

Network capability remains distinct from data egress.

A runtime-network implementation must have an explicit service/destination and egress posture before execution.

A stable endpoint URL cannot manufacture exact reproducibility if the provider silently changes the underlying service/model.

Authorization to access a network does not make a no-egress/no-network semantic commitment compatible with remote behavior.

## Authorization and runtime capabilities

Authorization remains current and action-specific.

Historical semantic commitment does not become a perpetual permission grant.

Runtime receives bounded operational authority equivalent to:

```text
committed requirement
∩ current authorization
∩ deployment/platform capability
∩ current recovery/fencing authority where material
```

Long-lived handles remain identifiers rather than bearer credentials.

Runtime code should not receive unrestricted canonical-store/catalog/network authority simply because it executes inside the same process/cluster.

## Secret boundary

Secret requirements/references may be durably represented when necessary; secret/credential values may not become canonical semantic state, activity snapshots, handles, manifests, Evidence, Provenance payload, checkpoints, ordinary telemetry/logs or reproducibility exports.

Secrets are resolved at use time through bounded current authority.

Credential rotation is normally operational when it preserves equivalent authorized access to the same committed destination/security domain. It does not by itself create a Strategy or activity revision.

Secret unavailability blocks/fails explicitly and cannot trigger ambient/developer credential fallback.

## Distributed runtime closure

Driver/coordinator readiness is insufficient.

Every material runtime role must satisfy its **role-specific** exact compatible closure.

The design does not require heterogeneous roles to contain identical bytes; it requires the aggregate Attempt to prove that each role can realize the top-level binding correctly.

Dynamic workers must inherit/prove closure before receiving material work. Deployment/profile-level proof is permitted so control state does not need one canonical row per executor.

Large Learned State/model/tokenizer/artifact loading remains distributed/shared/sharded/cacheable by exact identity and cannot universally require driver broadcast.

## Topology interaction

Implementation binding may declare topology/runtime limitations for single-table, time-series, multi-table shared-key and composite subjects.

Those limitations never redefine Data Meaning structural assertions, Generation scope or Constraint semantics.

An unsupported topology produces explicit incompatibility/limitation rather than simplification to a topology the implementation happens to support.

## Learned State interaction

Learned State remains logical semantic result identity.

Loading it requires an exact executable closure including state representation/codec/components/base artifacts and compatible runtime binding.

A loaded model/runtime object is transient realization, not historical Learned State identity.

## History / reproducibility

Where materially relevant, history must preserve enough information to explain which semantic Strategy/method and which exact implementation/dependency/runtime closure each Attempt used.

Security audit references may be retained where needed without embedding bearer secrets or turning Provenance into an access log.

If an exact runtime/service/dependency identity cannot later be reconstructed, reproducibility claims weaken rather than guessing.

## Self-contained baseline

The baseline still requires at least one source-derived/local free-form-text-capable Strategy path that needs no externally acquired pretrained model or runtime service after supported provisioning.

Optional local pretrained and runtime-network capabilities remain explicit extensions rather than hidden fallback or universal dependency.

## Phase 005-F / 005-I technology disposition

Earlier planning proposed concrete implementation choices including:

- `typing.Protocol` SPIs;
- specific runtime adapter/protocol names;
- Python entry-point discovery and `syngan.runtime_extensions`;
- a process-local runtime extension catalog;
- specific `RuntimeSpiVersion`/resource-kind spelling;
- `spark`/`torch` optional extras;
- concrete dependency/authorization/capability/secret types and package paths.

007-G retains their responsibility intent but reclassifies the exact Python/package/discovery/product choices as implementation candidates to reassess at explicit implementation re-entry.

## Falsification scenarios reviewed

007-G tested the architecture against:

- installed but untrusted extension code;
- driver-ready cluster with one executor missing a native dependency;
- self-contained source-derived text;
- explicitly provisioned pretrained text artifacts;
- runtime-network Strategy under a no-egress commitment;
- secret rotation during a long Attempt;
- authorization revocation after semantic commitment;
- runtime failure with a different compatible binding available for retry;
- an activity that explicitly committed one implementation for compliance;
- Python-style extension metadata whose import would execute untrusted code;
- code-executing Learned-State deserialization;
- mutable cache alias hiding the wrong exact artifact;
- remote API/model drift behind a stable endpoint;
- composite relational/time-series work using mixed runtime components.

The architecture remained coherent without a new concept, synchronization or ADR.

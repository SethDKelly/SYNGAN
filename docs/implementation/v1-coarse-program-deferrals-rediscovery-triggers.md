# v1 Coarse Program Design, Deferrals & Rediscovery Triggers

## Purpose

Preserve the likely post-MVP direction for SYNGAN without prematurely fixing a detailed v1 phase
graph, package set, provider matrix, release promise, or new product semantics before v0.x evidence
exists.

This authority is downstream of the v0.x MVP boundary, v0.x implementation program, MVP
qualification method, current support scope, engineering preflight, backlog, and the current
future-scope/rediscovery design authority.

It is intentionally coarse.

## Core principle

v1 is **evidence-derived future program scope**, not the union of everything deferred from v0.x.

The future program must be selected from:

- actual v0.x qualification results;
- explicit Phase 025 carry-forwards;
- measured provider/runtime/scale limitations;
- compatibility and migration evidence;
- concrete public-release or deployment objectives;
- explicit human product direction;
- current backlog items that remain relevant.

A backlog item, dormant residual, attractive feature, or historical idea does not become v1 scope
merely by existing.

## Meaning of "v1"

The label "v1" is a roadmap/program label only.

It does not currently mean:

- package version 1.0.0;
- public release;
- production provider support;
- enterprise-scale support;
- long-term compatibility guarantee;
- deployment/SLO readiness;
- inclusion of every candidate theme below.

The exact package-version relationship is deliberately deferred to Phase 026 after v0.x
qualification evidence exists.

## v1 activation boundary

Phase 026 is the only currently named post-MVP planning phase.

Phase 026 becomes **eligible**, not authorized, only after Phase 025 reaches a successful bounded-MVP
qualification outcome:

- PASS; or
- PASS WITH CARRY-FORWARD.

If Phase 025 is NOT READY TO EXIT, work remains in the v0.x repair/requalification loop. v1 program
selection does not bypass a failed MVP qualification.

A public v0.x release is not a prerequisite for Phase 026 unless future human product direction
makes it one.

## Candidate v1 themes

These themes are planning candidates, not commitments.

### V1-T01 — production provider/runtime qualification

Potential scope:

- exact Spark/Python/PyTorch/provider/runtime support matrix;
- provider-specific distributed realization;
- production recovery/fencing qualification;
- provider-specific portability/no-egress/security evidence.

Primary carried inputs include RR-016-06 and IRD-001/006/010.

Any resulting production-provider claim requires real E5 provider evidence. Reference or bounded
Spark-capable MVP evidence cannot substitute.

### V1-T02 — enterprise scale, performance, capacity & operational qualification

Potential scope:

- reproducible larger-scale benchmarks;
- workload envelopes;
- capacity/admission behavior;
- performance/support thresholds;
- operational SLO/SLA work where explicitly selected.

Primary carried inputs include RR-016-05 and IRD-003/004.

Ordinary operator/runtime capacity remains implementation/operations territory. If product scope
changes so SYNGAN itself owns durable budgets, credits, quota rights, spend, allocation, settlement,
or cross-activity resource accounting, the M8 resource/economic rediscovery trigger applies before
implementation.

### V1-T03 — public release, ecosystem, compatibility & API maturity

Potential scope:

- distribution-license decision and release metadata;
- current vulnerability/advisory clearance;
- public package/ecosystem/name review;
- explicit compatibility/readability/migration windows;
- broader Python support when evidence justifies it;
- stronger SDK/API/error/result/wire commitments.

Primary carried inputs include RR-016-01/02/03/04 and IRD-005/009.

This theme is claim-driven. v1 program work may proceed while the package remains unpublished unless
public distribution is explicitly selected.

### V1-T04 — broader Strategy, Evaluation, topology & text capability

Potential scope:

- broader Strategy families;
- additional Evaluation techniques;
- richer structured topology;
- advanced text-bearing capability;
- additional self-contained supported paths.

Primary carried inputs include BSD-004 and IRD-007/008 plus evidence from the v0.x topology/strategy
implementation.

Ordinary breadth that remains within existing purposes is F-1/F-2/F-4 extension work. It does not
justify new umbrella concepts.

### V1-T05 — deployment, enterprise integration & security-product realization

Potential scope:

- deployment/IaC when explicitly selected;
- concrete IAM/secret/network/KMS/DLP products;
- provider/external handoff integrations;
- production operational integration evidence.

Primary carried input includes IRD-002 and any deployment/provider carry-forward activated by v0.x.

External organizational governance remains external authority under F-6 unless SYNGAN product scope
changes to own the governance lifecycle itself.

## Theme-selection rule

Phase 026 must classify each candidate theme as exactly one of:

- SELECTED FOR V1 PROGRAM DECOMPOSITION;
- DEFERRED — INSUFFICIENT CURRENT PRODUCT/EVIDENCE NEED;
- EXTERNAL/NON-GOAL;
- REDISCOVERY REQUIRED BEFORE PROGRAM DECOMPOSITION.

No theme is selected merely because it appears in this document.

## Extension classification before v1 decomposition

Every proposed v1 capability must be checked against the current F-1..F-7 future-pressure model:

- F-1/F-2: existing concept purpose remains valid; proceed through ordinary design/architecture/
  implementation change control;
- F-3: new synchronization may be needed while state ownership remains current;
- F-4: application-family capability refinement may be needed;
- F-5: genuine concept rediscovery is mandatory before implementation planning;
- F-6: remains external authority/non-goal unless product scope explicitly changes;
- F-7: insufficient evidence; defer rather than speculate.

Architecture or semantic changes discovered inside F-1..F-4 still use normal Class 3/4 reopen
discipline. The classification does not waive change control.

## M8 rediscovery triggers

The four dormant M8 groups remain hard semantic gates.

### M8-R01 — formal composable privacy

Trigger when a selected product capability requires durable reusable/composable formal privacy
mechanism state such as budget allocation/reservation, privacy-loss consumption, composition,
remaining/exhausted state, or mechanism-specific guarantee/certificate state across occurrences.

Result: F-5. Perform mechanism/purpose-specific concept discovery before implementation. Do not
hide this lifecycle in Strategy, Generation, Evaluation, or Evidence.

### M8-R02 — product-owned governance, publication or independent output lifecycle

Trigger when SYNGAN itself would own durable approval/policy/release/publication/output lifecycle
state or actions such as approve/revoke, publish/unpublish, retire, manage distribution, or own
release-state transitions.

Result: F-5. Perform concept discovery before implementation.

External organizational governance and simple handoff remain F-6 unless product ownership changes.

### M8-R03 — independently reusable request/state/session lifecycle

Trigger when request/cohort/scenario/state semantics become independently reusable and managed
across occurrences, or when continuous synthesis introduces a durable session/subscription/feed
lifecycle with its own identity, pause/resume, reconfiguration, continuity, or retirement rules.

Result: F-5 or smallest-concept revalidation as directed by current design authority before
implementation.

Occurrence-local requests and bounded streaming windows remain ordinary extension when current
owners remain sufficient.

### M8-R04 — product-owned resource/economic lifecycle

Trigger when SYNGAN itself owns durable budgets, credits, resource rights, allocation, reservation,
consumption, exhaustion, transfer, settlement, chargeback, or cross-activity accounting.

Result: F-5. Perform concept discovery before implementation.

Provider/runtime capacity or operational admission alone does not activate this trigger.

## Generic rediscovery threshold

Outside the named M8 groups, fresh Jackson-style concept discovery is required when evidence shows
a genuinely independent product purpose with its own durable state/history, actions, lifecycle/
invariants, and reuse/cross-occurrence authority such that forcing the capability into an existing
concept would distort ownership or create shadow global state.

Speculative future possibility is not enough. The capability must also be sufficiently inside
current product intent to justify design ownership.

## Rediscovery routing

When a rediscovery trigger fires:

1. stop implementation/program decomposition for the affected capability;
2. record the trigger and evidence;
3. route to the smallest appropriate concept-discovery/design authority;
4. determine whether a new concept, synchronization, application-family change, or current-concept
   revision is actually needed;
5. propagate accepted semantic changes through dependence, synchronizations, experience/mapping,
   architecture, implementation authority, and qualification obligations as applicable;
6. only then return to implementation-program decomposition.

A rediscovery trigger is not permission to invent a concept. It is permission to ask the design
question again with current evidence.

## Evidence that may activate or reshape v1

Phase 026 must inspect at least:

- Phase 025 final decision and qualification ledger;
- carry-forwards and prohibited claims;
- support-scope state;
- v0.x API/compatibility experience;
- provider/runtime evidence and unresolved provider claims;
- performance/scale evidence;
- actual recovery/security limitations;
- backlog items still relevant to selected product goals;
- dormant M8 triggers;
- explicit human product/release objectives.

Phase 026 may reject or defer previously likely themes when evidence no longer supports them.

## Deliberately deferred decisions

017-H does not determine:

- whether the future package version is 1.0.0 or any other 1.x identifier;
- exact Phase 027+ count, names, or dependency graph;
- actual v1 IPKG manifests;
- exact provider/runtime versions;
- benchmark/SLO/SLA thresholds;
- exact Strategy/Evaluation algorithms;
- deployment/IaC topology;
- concrete IAM/KMS/DLP products;
- public release timing;
- distribution license;
- long-term compatibility windows;
- whether any M8 capability enters product scope.

Those decisions require the evidence and product direction available at Phase 026 or later.

## Phase 026 — v1 Evidence Re-entry, Scope Selection & Program Definition Start Gate

Phase 026 is a planning/re-entry phase, not product implementation.

Its role is to:

- consume the qualified v0.x evidence;
- reconcile Phase 025 carry-forwards and current backlog;
- classify proposed v1 scope using F-1..F-7;
- activate any required M8/design rediscovery before implementation planning;
- select the actual v1 themes;
- decide the future version/compatibility intent at the appropriate evidentiary strength;
- derive the detailed post-026 phase sequence only after those decisions are known;
- define qualification targets for the selected claims;
- preserve no-self-progression.

Phase 026 itself does not pre-authorize Phase 027 or any implementation package.

## Candidate qualification targets

If a theme is selected, its later program definition should use claim-appropriate evidence:

- production provider support -> real E5 provider qualification;
- enterprise-scale support -> reproducible scale evidence and explicit support envelope;
- public release -> release preflight, license decision, vulnerability review, compatibility policy;
- broader capability catalog -> E2-E4 behavioral/recovery/reproducibility qualification as relevant;
- deployment/operational claims -> environment-specific E5 evidence where the claim depends on it.

These are target types, not frozen thresholds.

## Relationship to v0.x residuals and backlog

RR-016 and backlog items are inputs, not automatic v1 requirements.

Closing a v0.x residual may remove a v1 candidate theme. New evidence may also create a more important
v1 theme not listed here, subject to normal authority and rediscovery discipline.

The backlog remains non-authoritative.

## Current authorization boundary

017-H establishes only the coarse future-program boundary.

Phase 026 and all v1 execution remain NOT AUTHORIZED. No v1 implementation package exists. No
package version changes. No M8 concept is accepted. No public release/provider/scale claim is made.
